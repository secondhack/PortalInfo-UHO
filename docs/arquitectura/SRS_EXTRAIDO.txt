1. INTRODUCCIÓN 
 
1.1 Nombre del Sistema 
PortalInfo UHO 
Sistema de Gestión de Contenidos para el Portal Cautivo Institucional de la Universidad de Holguín. 
 
1.2 Descripción General 
La Universidad de Holguín (UHO) cuenta con un Portal Cautivo basado en pfSense que intercepta el 
tráfico WiFi de los usuarios antes de autenticarlos y concederles acceso a Internet. Actualmente este 
portal muestra únicamente un formulario de autenticación (usuario y contraseña). 
 
PortalInfo UHO es un sistema que extiende este portal cautivo para convertirlo en un canal de 
comunicación institucional activo. El sistema consta de dos componentes principales: 
• Frontend del Portal Cautivo: página HTML+Bootstrap+JS optimizada para carga en 1-2 
segundos, ejecutada en el contexto pfSense, que muestra noticias, eventos, avisos, servicios y 
encuestas institucionales consumidos desde una API REST. 
• Backend de Administración (CMS): aplicación web desarrollada con Django y React, con base 
de datos PostgreSQL, que permite gestionar todos los contenidos del portal, controlar roles y 
permisos, aprobar publicaciones, analizar estadísticas de uso y auditar el acceso.

2. REQUERIMIENTOS GENERALES DE LA UHO 
 
Todo producto de software desarrollado para la Universidad de Holguín debe cumplir los siguientes 
requerimientos generales, establecidos por la política institucional de informatización: 
 
2.1 Centrado en el Usuario (UX) 
• El sistema debe estar diseñado priorizando la experiencia del usuario final, tanto para los 
visitantes del Portal Cautivo (estudiantes y trabajadores) como para los administradores y 
gestores de contenidos. 
• El Portal Cautivo debe ser perceptible y funcional en menos de 15 segundos por el usuario 
promedio. 
• La interfaz administrativa debe seguir principios de usabilidad: consistencia, feedback visual, 
prevención de errores y recuperación fácil ante errores. 
• El sistema debe ser accesible para usuarios con capacidades diferentes, siguiendo las pautas 
WCAG 2.1 nivel AA. 
 
2.2 Ciberseguridad 
• El sistema debe prever y mitigar los riesgos asociados a ciberseguridad en todas sus capas 
(frontend, API, backend, base de datos). 
• Se deben implementar mecanismos de seguridad para evitar vulnerabilidades conocidas: SQL 
Injection, XSS, CSRF, ataques de fuerza bruta, inyección de código, etc. 
• Todas las comunicaciones deben cifrarse mediante HTTPS/TLS. 
• Se deben generar logs estructurados de todas las acciones de los usuarios en el sistema 
(administrativo y portal cautivo), incluyendo: usuario, tipo_usuario, acción, IP, dispositivo, 
fecha/hora. 
• El sistema de logs del Portal Cautivo debe permitir detectar posibles usos compartidos de 
cuentas mediante análisis de IPs y dispositivos. 
• Se debe implementar un sistema de auditoría completo con trazabilidad de cambios en 
contenidos. 
 
2.3 Interoperabilidad 
• El sistema debe ser interoperable con los sistemas de registros primarios de la UHO: 
◦ SIGENU: Sistema de Gestión de Estudiantes. 
◦ ASSET: Sistema de Gestión de Trabajadores. 
◦ AGA_AUTH: Sistema de Autenticación Centralizada (auth.uho.edu.cu). 
• El sistema debe exponer una API REST con estándares internacionales (OpenAPI/Swagger) 
que facilite la integración con el ecosistema de aplicaciones de la UHO. 
• La autenticación de usuarios debe integrarse con AGA_AUTH, sin duplicar credenciales.

• El código fuente debe estar alojado y versionado en el GitLab de la UHO o en GitHub 
(github.com) si el GitLab institucional no estuviera activo. 
• El sistema debe garantizar actualizaciones sistemáticas desde el repositorio (CI/CD). 
• La aplicación debe estar desplegada en el entorno de desarrollo de la UHO o en un entorno 
local con Docker para su entrega. 
• Se debe incluir documentación técnica, de instalación, de uso y de mantenimiento. 
• El código debe seguir buenas prácticas de desarrollo: comentarios, nombres de variables 
descriptivos, separación de responsabilidades. 
 
2.5 Protección de Datos Personales 
• El sistema debe cumplir las regulaciones vigentes para la protección de datos personales de 
los usuarios. 
• Los datos personales (foto, nombre completo, DNI, tipo de usuario) provenientes de 
AGA_AUTH deben tratarse con confidencialidad y no almacenarse permanentemente en el 
sistema sin consentimiento. 
• Los logs de acceso deben almacenarse de forma segura y con acceso restringido. 
• Se debe informar al usuario qué datos se recopilan y con qué propósito. 
 
2.6 Identidad Visual y Estándares UHO 
• La interfaz (Portal Cautivo y panel administrativo) debe ajustarse al Manual de Identidad de la 
UHO: colores corporativos, tipografía, logo y estilo visual institucional. 
• Los sistemas web deben ser completamente responsivos (responsive design), adaptándose a 
dispositivos móviles, tabletas y computadoras de escritorio. 
 
2.7 Gestión de Nomencladores 
• Todos los nomencladores (áreas, departamentos, tipos de recursos, carreras, cargos, 
categorías de contenido, etc.) deben ser gestionables como CRUD completo desde el panel de 
administración. 
• No deben existir valores fijos en el código fuente que deberían ser configurables. 
 
2.8 Roles y Permisos 
• El sistema debe contar con un sistema de roles y permisos granular, configurable desde la 
administración. 
• Los roles mínimos requeridos son: Superadmin, Admin y Gestor de Contenidos. 
• Los permisos deben ser asignables por categoría de contenido (Noticias, Eventos, Avisos, 
Servicios, Encuestas y categorías creadas dinámicamente).

5. FLUJO GENERAL DEL SISTEMA 
 
5.1 Flujo del Usuario en el Portal Cautivo 
 
El siguiente flujo describe la experiencia del usuario final al conectarse a la red WiFi institucional: 
 
Paso Descripción 
1. Activación de WiFi El usuario activa la conexión WiFi en su dispositivo móvil o laptop. 
2. Detección por pfSense pfSense detecta que el usuario no está autenticado e intercepta la 
conexión. 
3. Redirección automática El navegador abre automáticamente el Portal Cautivo 
(HTML+Bootstrap+JS). 
4. Carga del portal (1-2 seg) El portal carga el formulario de login y realiza fetch() a la API para 
obtener noticias, eventos, avisos, servicios y encuestas activos. 
5. Visualización de contenidos El usuario puede navegar por las secciones de contenido (Noticias, 
Eventos, Avisos, Servicios, Encuestas) antes o después de 
autenticarse. 
6. Autenticación (Login) El usuario ingresa usuario y contraseña. El portal envía las 
credenciales a AGA_AUTH. Si son válidas, pfSense concede acceso 
a Internet. 
7. Confirmación visual El portal muestra el nombre completo y foto del usuario (datos de 
AGA_AUTH). El sistema registra el acceso en el log. 
8. Registro de visualizaciones El portal reporta via API qué secciones e ítems visualizó el usuario 
(para estadísticas). 
9. Acceso a Internet El usuario navega libremente hasta que cierra sesión o expira el 
tiempo de conexión. 
 
5.2 Flujo de Publicación de Contenidos 
 
Paso Actor / Descripción 
1. Creación del contenido El Gestor de Contenidos inicia sesión en el panel administrativo con 
sus credenciales UHO (AGA_AUTH). 
2. Redacción El Gestor crea un nuevo ítem (ej: noticia) completando los campos 
requeridos dentro de los límites de caracteres configurados. 
3. Configuración de vigencia El Gestor selecciona el período de visibilidad del contenido (hoy, 3 
días, semana, mes, siempre o rango). 
4. Enviar a publicación El Gestor hace clic en 'Publicar'. El sistema valida el contenido y lo 
marca como 'Pendiente de aprobación'. 
5. Alerta al Admin El sistema notifica al Admin (campanita + correo) que hay un nuevo 
contenido pendiente.

6.1 Stack Tecnológico 
 
Componente Tecnología

6.2 Diagrama de Componentes (descripción) 
 
La arquitectura del sistema se organiza en tres capas principales: 
 
• Capa de Presentación: (1) Portal Cautivo HTML en pfSense – consume la API REST. (2) Panel 
de Administración React – interfaz SPA para gestores y admins. 
• Capa de Negocio y API: Django con Django REST Framework expone todos los endpoints. 
Gestiona la lógica de negocio: aprobación de contenidos, control de vigencia, roles y permisos, 
notificaciones, logs. 
• Capa de Datos: PostgreSQL almacena todos los datos del sistema. El acceso a datos se 
realiza exclusivamente a través de Django ORM. 
• Servicios Externos: AGA_AUTH para autenticación. SMTP para envío de correos. (Futuro) 
SIGENU y ASSET para integración de datos de usuarios.

7. CASOS DE USO PRINCIPALES 
 
CU-01: Conectarse a la red WiFi y ver contenidos 
Campo Detalle 
Actor principal Usuario (Estudiante o Trabajador) 
Precondición El usuario tiene un dispositivo WiFi y credenciales UHO válidas 
Flujo principal 1. Usuario activa WiFi → 2. pfSense muestra portal → 3. Portal carga 
contenidos via API → 4. Usuario navega secciones → 5. Usuario 
introduce credenciales → 6. pfSense autentica via AGA_AUTH → 7. Se 
registra el acceso → 8. Usuario accede a Internet 
Flujo alternativo Si la API no responde: el portal muestra solo el formulario de login. La 
autenticación sigue funcionando. 
Postcondición El usuario tiene acceso a Internet. El sistema registra el evento de acceso. 
 
CU-02: Gestor crea y publica una noticia 
Campo Detalle 
Actor principal Gestor de Contenidos 
Precondición El gestor tiene cuenta en el sistema con permiso de gestión de Noticias 
Flujo principal 1. Gestor inicia sesión con credenciales UHO → 2. Navega a Gestión de 
Noticias → 3. Crea nueva noticia (título, contenido, área, vigencia) → 4. 
Sistema valida límites de caracteres → 5. Gestor hace clic en 'Publicar' → 
6. Sistema notifica al Admin → 7. Admin aprueba → 8. Noticia aparece en 
el portal 
Flujo alternativo Si se excede el límite de caracteres: el sistema muestra advertencia y no 
permite guardar. Si se excede la cantidad máxima visible: el sistema 
alerta pero permite enviar a aprobación. 
Postcondición La noticia está activa en el portal cautivo y visible para todos los usuarios 
WiFi. 
 
CU-03: Admin aprueba contenido pendiente 
Campo Detalle 
Actor principal Admin 
Precondición Existe contenido pendiente de aprobación 
Flujo principal 1. Admin recibe notificación (campanita/correo) → 2. Abre cola de 
aprobación → 3. Revisa el contenido → 4. Aprueba o rechaza con motivo 
→ 5. Sistema activa/rechaza el contenido → 6. Sistema notifica al Gestor 
Postcondición El contenido queda activo (si aprobado) o en estado rechazado (si 
rechazado).

9. RESTRICCIONES Y REGLAS DE NEGOCIO 
 
10. El portal cautivo (HTML en pfSense) NO debe ser modificado para cambios de contenido ni de 
configuración de secciones. Todos los cambios deben hacerse desde el backend. 
11. El portal cautivo SOLO puede usar HTML5, Bootstrap 5 y JavaScript nativo. No se permite el 
uso de frameworks adicionales (React, Vue, Angular) en el frontend de pfSense. 
12. Los recursos de Bootstrap y JS utilizados en el portal cautivo deben estar embebidos o 
servidos localmente (sin CDN externo), para garantizar carga en 1-2 segundos incluso sin 
acceso a Internet. 
13. El portal cautivo no debe cargar imágenes de contenido, videos ni documentos. Solo texto y 
links. 
14. La autenticación administrativa SOLO se permite para usuarios registrados previamente en el 
sistema, aunque sus credenciales AGA_AUTH sean válidas. 
15. Todo contenido creado por un Gestor requiere aprobación de un Admin antes de ser publicado 
en el portal. 
16. El Superadmin no puede ser eliminado del sistema. 
17. Los logs de acceso no deben poder eliminarse manualmente (solo por política de retención 
configurada). 
18. Las contraseñas de usuarios NO se almacenan en la base de datos local. La autenticación es 
100% delegada a AGA_AUTH. 
19. El sistema debe seguir funcionando (portal cautivo y autenticación) aunque la API de 
contenidos no esté disponible temporalmente.
